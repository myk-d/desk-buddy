# Project: Beak Buddy Firmware

## Overview

C++ firmware for the **Beak Buddy** desktop gadget: an ESP32-S3 driving a 2.8" ILI9341 color TFT (the main face/eyes display) and an addressable NeoPixel for ambient color. It's controlled two ways at once:

- **USB serial** (115200 8N1) from the companion Electron app (`../desktop-app/`) — the primary control path.
- **WiFi**, once configured — the device hosts its own HTTP server so ambient notifications keep working with the desktop app fully closed (WiFi OTA is disabled, see "Known hardware limitation"). Claude Code hooks *can* post here directly too, but in practice the desktop app should be kept running for accurate stats (see `../desktop-app/CLAUDE.md`).

Board: ESP32-S3 N16R8 (16MB flash, 8MB PSRAM). Custom partition table (`partitions_custom.csv`) — a single 4MB "factory" app slot (no OTA) + an 11.5MB LittleFS partition holding **every** character animation as a GIF (idle/focus/relax/love/error/startup, plus the ~84 "bonus" ones — see "Taby animations" below). The app binary itself is tiny (~1.15MB / 7% of the whole 16MB chip) — it's the GIF data on the filesystem partition that actually uses the flash budget, and that's deliberately *not* linked into the firmware binary (90 full-canvas character animations baked in as PROGMEM would be tens of MB, many times over a single 6.25MB OTA slot).

## File layout

Everything is `#pragma once` headers with inline function bodies, `#include`d directly into `main.cpp`'s single translation unit — a deliberate unity build, not real multi-TU compilation. There's exactly one place (`main.cpp`'s include block) where forward declarations exist, for the handful of cases where an early-included file needs to call a function defined later in the chain.

| File | Contents |
|---|---|
| `main.cpp` | Doc comment (protocol reference), includes in dependency order, `setup()`, `loop()` |
| `display.h` | Pin/baud defines, `LGFX_BeakBuddy` (LovyanGFX driver class), `lcd`/`pixels` globals, color constants |
| `gaze_state.h` | `GazeState` enum, `currentState`/`pomoLocked`/`tabyIsLooping`/`stateBeforeTaby`, Claude/notify state globals |
| `pomodoro_screen.h` | Full-screen Pomodoro timer display |
| `claude_screen.h` | Full-screen Claude Code status display + **`enterState()`**, the central state-machine dispatcher every screen module funnels through — also where idle/focus/relax/love/error/startup each load their fixed Taby GIF id |
| `notify_screen.h` | Generic ambient-status notification screen (`/notify`) — not tied to any specific integration |
| `sensor_screen.h` | Climate screen — AHT20 (temp/humidity) + BMP280 (pressure) over I2C. Pops up on its own every 5 minutes (not just via `#ANIM:sensor`), shows for 15s, auto-reverts to whatever was showing before |
| `taby_gif_player.h` | `TabyGifPlayer`/`GIFDraw`/LittleFS file callbacks — decodes **every** character animation (not just the ~84 bonus ones) straight from `/taby/<id>.gif` on LittleFS via `bitbank2/AnimatedGIF`, nearest-neighbor-downscaling 2x (280×456 → 140×228) right in the draw callback |
| `taby_screen.h` | `playTabyAnimation(id)`/`pollTabyRandomShow()` — the ~84 "bonus" Taby character animations (`#TABY:<id>`, plus random pop-ups), looked up by id in `taby_registry.h` |
| `taby_registry.h` | Auto-generated by a one-off conversion script (not in this repo) — just `{id, loopAnim}` pairs for the ~84 bonus animations, no pixel data (that lives in `data/taby/*.gif`, uploaded to LittleFS separately from the firmware binary). The 6 dedicated states don't need a registry lookup — their id is hardcoded directly in `enterState()` |
| `wifi_manager.h` | WiFi connect/scan/NVS credential storage, mDNS, NTP kickoff, `wifiPoll()` |
| `web_server.h` | The device's own HTTP server — every route handler lives here. `/update` (WiFi OTA) is disabled (501) — see "Known hardware limitation" below |
| `serial_protocol.h` | `handlePacket()`/`readSerial()` — the USB serial command dispatcher |
| `data/taby/*.gif` | ~90 Taby character GIFs (280×456) — the 6 dedicated states (`startup`, `idle_01_loop`, `working_loop`, `relaxing_01_loop`, `love_01`, `angry_01_loop`) plus the ~84 bonus ones, ~9.93MB total, uploaded to the LittleFS partition via `pio run --target uploadfs` — **not** part of the compiled firmware binary, so a plain `--target upload` doesn't touch these |

Adding a new full-screen feature gets its own `*_screen.h` (mirroring `pomodoro_screen.h`/`claude_screen.h`/`notify_screen.h`, each with an `applyX()` + `pollXTimeout()` pair for non-blocking auto-revert-to-idle). Adding a new HTTP endpoint goes in `web_server.h`.

## Taby animations

Every character animation on this device — idle/focus/relax/love/error/startup *and* the ~84 "bonus" ones (`#TABY:<id>`) — is a GIF ported from the original "Taby" device and played back from LittleFS, not PROGMEM. The 6 dedicated states used to be our own small eye-window PROGMEM animations (`boot.h`/`idle.h`/`work.h`/`happy.h`/`love.h`/`angry.h`) — those files are gone; `enterState()` (`claude_screen.h`) now loads a fixed Taby id for each of them directly through `tabyPlayer` (`taby_gif_player.h`), the same player the ~84 bonus animations use. `taby_registry.h` lists every bonus id (the 6 dedicated ones don't need a registry entry — their id is hardcoded).

Tried baking all ~84 bonus animations into PROGMEM first — came out to **34MB** (full-canvas character animations compress far worse with our simple delta-RLE than the original small eye-only crops did), many times over a single 6.25MB OTA app slot. The original GIFs at native resolution are only **9.93MB total** for all ~90, so they live on a dedicated LittleFS partition instead (`partitions_custom.csv`) and get decoded frame-by-frame at runtime via `bitbank2/AnimatedGIF` (`taby_gif_player.h`) — nothing animation-related is linked into the firmware binary itself anymore.

This is why the partition table changed from the stock dual-OTA `default_16MB.csv` to a single-app-slot `partitions_custom.csv`, and why WiFi OTA (`POST /update`) is now disabled (501) — there's no second app slot for `Update.h` to ping-pong into anymore. Confirmed acceptable: this device is already USB/BOOT-button-only for flashing in practice.

Besides `#TABY:<id>` (deliberate trigger), `pollTabyRandomShow()` (`taby_screen.h`) also fires on its own — a random *one-shot* bonus reaction (never an ambient loop) every 3-10 minutes (rerolled each time, not a fixed interval), while an ambient state (idle/focus/relax/love/error) is already showing. Never interrupts Pomodoro/Claude/Notify/Climate/an already-running Taby animation/startup.

`ST_FOCUS` (`enterState()`, `claude_screen.h`) cycles `working_laptop_bored_loop`/`excited_loop`/`normal_loop` round-robin each time it's (re-)entered (65% of the time — the rotation just advances), the rest of the time throwing in a different "Work & focus" loop instead (`working_loop`/`busy_loop`/`workspaces_loop`/`searching_loop`) without disturbing the round-robin's position. `working_laptop_in`/`working_laptop_loop` and the three `calm_work_*_f000` stills were deliberately dropped from the pool. The one-shot transitions in that category (`working_in`, `lockin`, `posture_check`, `copy_paste`, `workspaces_in`) are skipped too: FOCUS has to stay put with nothing to auto-revert it, the way `#TABY:`'s one-shots do.

**NeoPixel color** is fixed per *state*, not per individual animation — e.g. every FOCUS pick (whichever of the above plays) shows the same color for that entry. `setRandomNeo()` (`claude_screen.h`) picks from a curated palette, rerolled each time a state is (re-)entered, for every ambient/reaction state (STARTUP/FOCUS/RELAX/LOVE/ERROR/TABY) — except `ST_IDLE` (fixed purple) and `ST_CLAUDE` (its own severity-graded scheme, `claudeSeverityRGB()`/`pollClaudeActivityPulse()`, untouched — the claude_in/claude_loop overlay doesn't call `setNeo()` at all). Pomodoro's colors are also left alone (they deliberately match the desktop app's Tailwind colors).

The `ST_CLAUDE` dashboard (two usage-ring cards) similarly gets Claude's own two animations mixed in (`playClaudeAnim()`/`pollClaudeAnim()`, `claude_screen.h`) — `claude_in` plays once as a brief intro whenever Claude genuinely (re-)starts working (not on every repeat "working" ping from PreToolUse — `applyClaudeState()`'s `alreadyThere` check filters those out already), then `pollClaudeAnim()` reverts to the dashboard; while still "working", `claude_loop` interleaves in for `CLAUDE_ANIM_DISPLAY_MS` (4s) every 1-3 minutes (rerolled, same pattern as the Taby random pop-ups), then reverts again. `currentState` stays `ST_CLAUDE` throughout — this is a what's-drawn overlay, not a state change, so Claude's own lock/auto-revert/severity-color logic is untouched.

## Serial protocol (USB, 115200 8N1)

Packets are `#COMMAND:args\n`. Current commands:

| Command | Effect |
|---|---|
| `#ANIM:<name>` | `startup` / `idle` / `focus` / `relax` / `love` / `error` / `pomowork` / `pomobreak` / `pomolongbreak` / `sensor` |
| `#TABY:<id>` | Plays one of ~84 "bonus" Taby character animations by id (see `taby_registry.h`) — looping ids become the new ambient state, one-shot ids auto-revert to whatever was showing before once finished |
| `#R` | Software restart (`ESP.restart()`) |
| `#VERSION` | Replies `FIRMWARE:<version>` |
| `#CLAUDE:<sub>` | Claude Code full-screen status: `idle` / `thinking` / `working` / `done` / `waiting` |
| `#USAGE:<5hPct>,<5hSecs>,<7dPct>,<7dSecs>[,<email>]` | Session/weekly usage bars (app precomputes the countdown — firmware has no RTC of its own until NTP syncs); optional trailing email is shown above the cards and persists until a non-empty one arrives again |
| `#TIME:<secondsLeft>:<total>` | Updates the Pomodoro timer/progress bar (only while in a Pomodoro state) |
| `#WIFI:SCAN` | Async — replies `WIFI_NETWORKS:ssid,rssi;...` once the scan completes (non-blocking; `loop()` keeps ticking during the ~6-7s scan) |
| `#WIFI:CONNECT:<token>:<ssid>,<password>` | Saves credentials + connects; replies `WIFI_STATUS:connected,<ip>` or `WIFI_STATUS:failed` |
| `#WIFI:STATUS` | Current connection state |
| `#WIFI:FORGET` | Clears saved credentials, disconnects |

`pomoLocked` (set while in any Pomodoro state) blocks `#CLAUDE:`/most `#ANIM:` commands from interrupting a focus session — `idle` and the Pomodoro anims themselves are always allowed through.

## WiFi HTTP server (once configured)

Reachable at `http://beak-buddy.local` (mDNS) once WiFi is set up via the desktop app (credentials are sent once over USB, never typed on the device). This is what lets `/notify` work with the app fully closed — Claude Code stats, however, are more reliable with the desktop app left running.

| Route | Auth | Purpose |
|---|---|---|
| `POST /claude-state` | `X-Beak-Token` | Same as `#CLAUDE:` over serial |
| `POST /claude-usage` | `X-Beak-Token` | Same as `#USAGE:` over serial |
| `POST /notify` | `X-Beak-Token` | Generic ambient-status notification: `{title, message, color, durationMs}` — not tied to Claude Code, auto-reverts to idle |
| `POST /update` | `X-Beak-Token` | **Disabled** (501) — no second app slot for `Update.h` to flash into since the partition table moved to a single app slot + LittleFS (see "Taby animations"). Flash via USB/BOOT button instead |
| `GET /status.json` | none | Diagnostics: heap, RSSI, uptime, current state, firmware version, WiFi SSID, NTP sync status/time |
| `GET /` | none | Small human-readable dashboard, polls `/status.json` client-side |

Read-only/low-sensitivity routes are intentionally unauthenticated (LAN-only, matching common IoT status-page convention); anything that changes device state requires the token. Custom headers (`X-Beak-Token`) must be explicitly registered via `beakServer.collectHeaders()` — `WebServer` silently returns `""` for any header not on that list, a bug hit once already.

State-changing HTTP handlers relay back over USB serial (`CLAUDE_RELAY:`, `USAGE_RELAY:`) when connected, so the desktop app's own UI stays in sync even when the update arrived via WiFi and bypassed the app entirely.

## Climate sensor (AHT20+BMP280, I2C)

Optional add-on, checked for at boot (`sensorsBegin()` in `sensor_screen.h`) — `sensorAvailable` stays `false` and the Climate screen just shows "Sensor not found" if it's missing or not wired yet, nothing else is affected. Wired to `PIN_I2C_SDA`/`PIN_I2C_SCL` (`display.h`, currently GPIO 4/5) — **picked without a physical board to verify against** (the sensor was still in transit when this was written), so confirm those are actually free/broken-out pins before wiring and update the defines if not. The BMP280 half can be strapped to I2C address `0x76` or `0x77` depending on the breakout; `sensorsBegin()` tries both.

## Known hardware limitation

This device's Linux USB-CDC driver doesn't support the DTR/RTS toggling `esptool`'s default bootloader-reset sequence relies on — `pio run --target upload` fails with "No serial data received." The desktop app used to work around this with its own 1200-baud-touch reset trick (`electron/flasher.ts`), but that capability was deliberately removed from the app — **flashing is now fully manual**: hold the board's BOOT button (or tap it right as you plug in / while `pio run --target upload` is waiting) to force it into bootloader mode before the upload proceeds. Claude Code cannot flash the device directly in this environment either way — compiling is verifiable (`~/.platformio/penv/bin/pio run`, never the bare `pio`), flashing always needs the user physically present at the device.

**Two separate uploads now, both need BOOT held**: `pio run --target upload` (firmware binary → the `factory` app partition) and `pio run --target uploadfs` (the `data/taby/*.gif` files → the LittleFS partition). The GIFs only need re-uploading when `data/` changes — a firmware-only change doesn't require `uploadfs` again, and vice versa.

See `.claude/skills/flash-firmware/` and `.claude/skills/test-device/` (repo root) for the exact procedures, or delegate to the `firmware-checker`/`device-tester` agents.
